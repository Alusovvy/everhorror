# ai-task

Modes (the argument after `/ai-task`): **`analyze NN`**, **`implement NN`**, **`fix NN`**, **`review NN`**; `status` and `close NN` plus everything only a terminal session does: [docs/agent/ai-task-terminal.md](../../../docs/agent/ai-task-terminal.md). A bare "zrób task_12" means `analyze` if the task has no resolved plan yet, otherwise `implement`.

Paths: [CLAUDE.md#places](../../../CLAUDE.md#places). Read [CLAUDE.md](../../../CLAUDE.md) first (systems: `docs/agent/README.md`; tests and release: `tools/README.md`). Rules from `docs/ai-tasks/INFO.md`: never edit the task's requirements section ("Wymagania:" / "Requierments"), typos included; the task file always ends with **Podsumowanie**, in the task's language (task_02+ Polish); report in the task file and briefly in chat.

**Dashboard lock (every mode).** Check it as described in [CLAUDE.md#dashboard-lock](../../../CLAUDE.md#dashboard-lock). If another live run holds it, stop and report who; never delete it.

Process and source precedence: `C:/dev/gamedev/everhorror/specification/WORKFLOW.md`. Roland owns all active sections; keep original authorship and attribute chat decisions. Never fill a human zone (list and rules: [docs/human-tasks/INFO.md](../../../docs/human-tasks/INFO.md#strefy-człowieka)); your automated checks go only in the task report or under `## Wyniki automatu (agent)` in the sheet. A merge or a green check is not human verification. A new gameplay request first becomes accepted spec text, then a task with its spec SHA (plan §3 pkt 2, `docs/analizy/plan.md`); never implement it directly on main. A bounded documentation/tooling request follows its authorized scope.

Helpers in `.claude/agents/` get the working directory, the files and one concrete question, return only conclusions and never edit: `lore-checker` (Polish lines or world facts vs. the canon), `test-runner` (named scenarios → RESULT table; wait for it), `convention-reviewer` (the diff vs. `CLAUDE.md`).

## Dashboard runs
You are in one when `EVERHORROR_DASHBOARD_RUN` is set or the appended system prompt starts with `# Przebieg z dashboardu`. Roland's click started you: the skill call is the whole job. **What a run may and may not do (write roots per kind, shell forms, git and push, ledger and spec commits, `node`, builds, the three finishing lines) is only in [docs/agent/run-rules.md](../../../docs/agent/run-rules.md), which the contract appends; a stricter contract wins.** A PreToolUse guard blocks forbidden commands and writes (a block is a rule; use the form it suggests); an audit flags violations afterwards. Other runs may be active beside you (up to 3 analyses and 3 implementations, D-33): you write only your own task file and branch copy.
- **Non-interactive.** Never ask or wait. When Roland has to decide, write one decision card (D-03) `C:/dev/gamedev/everhorror/specification/zgloszenia/<YYYY-MM-DD>_task<NN>-<topic>.md` (ASCII name) from `szablony/decyzja.md`: `Rodzaj: decyzja`, `Zadanie: task_NN`, one table `| # | Pytanie | Opcje | Rekomendacja | Twój wybór |` for all questions (recommendation first, `Twój wybór` empty), `## Decyzja` = "Do rozstrzygnięcia." Set the header field `Klasa:` to one of `odwracalna` / `kanon` / `bezpieczeństwo`: `odwracalna` only when every question has a recommendation **a)**–**c)** that names an existing option and the effect can be undone later; when in doubt `kanon` (with Roland's auto-recommendations mode on, D-37, the server resolves an `odwracalna` card by its recommendations; `kanon` and `bezpieczeństwo` always wait for Roland). Every option must be understandable without the rest of the card: it says in words what is chosen, and every code (B1, A2…) is explained either by a list item `- B1: …` under "Możliwości i rekomendacja" or on the spot (`**a)** B1 (scena zaznaczenia żyły) + B2 (przyciemnienie przy pracy)`); a gloss after the last code does not explain the earlier ones, and an unexplained code gives the lint warning `OPCJA_KOD_BEZ_OPISU` (rule ids like CZAS-10 are exempt). At most five open cards (plan §3). Lint, commit the card (run-rules §3) naming only its path, link it from the task file, write in the Plan section the line `Plan zależy od wyboru: tak|nie` (tak = the Plan changes with the answer), stop with `STATUS: czeka-na-decyzje`. After the answer the server appends `## Decyzje z karty <plik>` to the task file (and starts a short run to update the Plan when the line says `tak`); that section is binding, the analysis is not resumed. A `review` run writes no card: it states the open decision in `podsumowanie` with the verdict `blokada`.
- **Main copy.** Docs you create or change there (the task file with its report and its `## Część arkusza`) stay uncommitted. Do not `git mv` task files or sheets (`/spec-sync finalize` moves the task file; Roland's click closes a sheet). `docs/human-tasks/**`, including the register `BUILDY.md`, is the server's: a run does not write there (D-38).
- **Code** only in the branch copy (git worktree) named in the contract, on the task branch; Godot only with `--path` set to it. Tests by name through `test-runner`; the full suite only when the contract says "user approved full suite".
- **Human zones and requirements.** The audit also checks what a sheet says about itself (`SHEET_STATE`): never add or change the header notes `zastąpione …` and `niesprawdzone przez człowieka` or a `Zwolnienie:` line, rename a human column (`wynik` to `Wynik automatu`), put `(agent)` in the heading of a human table, or delete a sheet's empty rows.

## analyze NN
1. Read the task, `INFO.md`, any factcheck or decision of a task it depends on, and the code and spec parts it touches ("Dla agenta"). If an earlier task ("Kolejność") is still open, say so.
2. Below the requirements (after the `---` / agent marker) write **Analiza** (how it works today, gaps, risks) and **Plan** (steps, files, tests, spec/docs updates). In **Plan** write one line `Pliki: path1, dir/path2, …`: the game files and directories the implementation will touch, repo-relative, the task's own docs excluded (the dashboard uses it to allow parallel implementations and to stop the chain when the plan leaves it).
3. Open questions: a decision card (D-03), linked from the task (terminal: AskUserQuestion). Legacy `decision-task-NN.md` files are read-only history.
4. Report: what the task needs, what you ask.

## implement NN
A task with the header line `Źródło: specyfikacja` was written by `/spec-tasks`; also follow **Spec tasks**.

1. **Preconditions.** Every decision is resolved (cards with `Zadanie: task_NN` ✅ or closed, a legacy file in `human-tasks/done/`, or the user answered in chat); dependencies are implemented; a filled-in sheet of a related task has been read, its bugs fixed or out of scope. Otherwise stop and say what (`STATUS: czeka-na-decyzje` for a decision, else `blad`).
2. **Implement** following the conventions in `CLAUDE.md` (generators for generated scenes, Silesian keys, dialogue tags, DIA-2 guards, number helpers, `--import`).
3. **Lore.** New or changed Polish lines, or facts about people, places, magic or factions: spawn `lore-checker` with the lines (`file:line`) and the facts they assert. Fix real contradictions; route unresolved canon to Roland with sources and a recommendation, keeping deliberate unknowns and `[ROBOCZE]`.
4. **Tests.** `test-runner` with `unit lint dialogue` plus the scenarios of the touched systems (map: `tools/README.md`); say whether `.dialogue` files or new `class_name` scripts changed (it must `--import` first). A branch copy made by the dashboard already has the Godot import cache; run one short `--headless --path <worktree> --import` before the first test. The full suite only on explicit approval. Fix failures caused by the change; report others instead of widening it. The server repeats the tests after the run: they decide, not your word.
5. **Review.** `convention-reviewer` on the uncommitted diff, naming the task; fix findings, re-run `test-runner` on the scenarios they touch.
6. **Docs.**
   - Sheet part (level `rozgrywka` only; read the `Poziom:` line of the task file, no line = `rozgrywka`; `tekst` and `narzędzia` have no part, their evidence is the tests and a screenshot in the report, and they pass `--sheet -` to the ledger). **Review cycle (D-38): you do not create, extend or touch any sheet and write nothing in `docs/human-tasks/`** (the guard blocks it). Write the part in **your own task file**, in the main copy, Polish: a section `## Część arkusza` (template: `docs/ai-tasks/task_template.md`) with `### Co zostało dodane` (what changed, in the player's words, rule IDs), `### Test` (a table `| # | co sprawdzić | jak | oczekiwany wynik |`, no human columns: the server adds empty `wynik` and `uwagi` when it assembles the sheet; a table that already has human columns, such as a survey with a 1-7 scale, keeps them empty) and `### Wyniki automatu (agent)` (your real test commands and results). Plan the rows so that one person can play the whole change on one build of `master`. The server assembles one sheet `factcheck-cykl-NN.md` and the build for the whole cycle once the tasks of the cycle are merged; the part is copied word for word, in the order of the merges. The contract names the cycle that collects (`factcheck-cykl-NN.md`) for the ledger. Never write a `> Build:` line, never export, zip or stamp the game by hand: there is no build after a run, the server makes one build per cycle. A play session (PT) is a different thing: `playtest_template.md`, made by a person's request, rules in `docs/human-tasks/INFO.md`.
   - Spec: update the rules; mark self-decided details **[ROBOCZE]**; code pointers under "Dla agenta"; numbers in `07_balans.md`. Add **no new row** to "Zmiany agenta poza specyfikacją" (D-23): an urgent fix of a bug that violates an existing rule needs none; any other game change is first a ⬜ rule. Lint the spec (0 errors).
   - Update where the changed fact lives: `CLAUDE.md` (rules, conventions), `docs/agent/README.md` (systems), `tools/README.md` (tests, release). The old duplicated design docs were removed (D-02); `docs/archiwum/MECHANICS.md` is history.
7. **Task file.** Fill in "Co zostało zrobione" (one subsection per requirement), "Decyzje i założenia", "Czego potrzebuję od Ciebie", "Test" (RESULT lines; the part for the person is the section `## Część arkusza`), "Podsumowanie" last. A spec task stays in `docs/ai-tasks/` until its branch is merged; a dashboard run never moves a task file (a chat task in a terminal: [ai-task-terminal.md](../../../docs/agent/ai-task-terminal.md#zadanie-z-czatu-zamknięcie-pliku)).
8. **Report**, briefly: changes, test results, what the part of the sheet asks the person to check, open questions.

## Spec tasks
Tasks with `Źródło: specyfikacja <sha7>`, created by `/spec-tasks`:
- **Where.** Branch `spec/<YYYY-MM-DD>-task<NN>` in its own branch copy; never switch branches in the main copy. In a dashboard run the branch and its copy already exist and are switched (the contract names them): create and switch nothing. Up to three open `spec/*` branches at once (D-33): a 🔧/🧪 row in "Na gałęziach" beyond that means stop and name it. Give the worktree path to `test-runner` and `convention-reviewer`. Terminal: [ai-task-terminal.md](../../../docs/agent/ai-task-terminal.md#kopia-gałęzi-w-terminalu).
- **Requirements** are rule quotes; the spec text of those IDs (and "Dla agenta") is binding. A self-decided detail goes into the spec as **[ROBOCZE]**. If the spec contradicts itself, write a decision card; don't guess.
- **Commit** code and current docs on the branch as `task_NN: <short Polish summary>`, IDs in the body. The task file with its `## Część arkusza` is **not** committed there (it lives in the main copy). Never commit to or merge into `master`.
- **Ledger.** One command writes both rows (never edit `WDROZENIA.md`): `node <spec>/dashboard/cli.ts ledger set-branch --branch spec/<date>-task<NN> --commit <sha7> --changes "<IDs>, task_NN" --sheet docs/human-tasks/factcheck-cykl-<NN>.md --status do-sprawdzenia --task-status na-galezi --message "[agent] spec/<date>-task<NN>: wdrożone na gałęzi, do sprawdzenia"`. `--sheet` is the sheet of the cycle the contract names (the server makes that file when the cycle's build is made; the path is only a pointer; `--sheet -` for a task without a part — omitting it would write the old default name). Don't flip ⬜→✅ (finalize does). Lint (0 errors), push (run-rules §3).
- **Tool and documentation tasks** (`Rodzaj: narzędzia` / `dokumentacja`) have no spec rules or spec commit, but the same branch, copy, report and ledger command with `--commit —` and `--changes "task_NN"`; no "W zadaniach" row (the command warns that it skipped `--task-status`); never gameplay. The dashboard runs them like any other task.
- **Report** with how to try it: say which rows of the part to play (there is no branch build: the one playable build is the build of the cycle, made by the server from `master` after the merges; the branch preview is only for debugging). You never merge: Roland's click or the dashboard's automatic merge (D-35, D-36).

## review NN
Read-only review of a built branch. It writes and commits nothing.
1. Find the branch and the worktree (the contract names them). Read `git -C <worktree> diff master...<branch>` (also `--stat`; `show <branch>:<path>` for whole files), the task's requirements and report in the main copy, and its part of the sheet (`## Część arkusza`). Never switch the worktree or the main copy. If the worktree is not on the branch (`branch --show-current`), skip the tests and say so. One short `--headless --path <worktree> --import` before the tests.
2. Judge against: every requirement; the spec rules of its IDs and "Dla agenta" (pointers right, `[ROBOCZE]` on self-decided details, numbers in `07_balans.md`, both ledger rows at 🧪); the decisions it relies on; the `CLAUDE.md` conventions; the process rules (the part of the sheet in the task file, nothing written in `docs/human-tasks/`, human zones empty, requirements byte-identical, the report ends with "Podsumowanie").
3. You may spawn `convention-reviewer` (range `master...<branch>`) and `lore-checker`, and run named short tests through `test-runner` (`unit lint dialogue` plus the touched scenarios; they write into `reports/` of the branch copy). Never the full suite.
4. Final answer, nothing after it: one JSON object `{werdykt, wymagania, ustalenia, podsumowanie}`: `werdykt` = `gotowe` (no `błąd`, every requirement `spełnione`, named tests pass), `poprawki`, or `blokada` (must not be merged: a human zone filled, requirements edited, a decision missing, a test failing because of the change); `wymagania` = per requirement `{nr, stan: spełnione|częściowo|brak, dowod}` (file, line or test); `ustalenia` = `{waga: błąd|uwaga, plik?, linia?, opis}`, most serious first (`błąd` must be fixed before the merge); `podsumowanie` = two or three Polish sentences for Roland. A dashboard run passes the schema (`--json-schema`): return the object via structured output, no STATUS lines. In a terminal print a JSON block.

## fix NN
Corrections on a built branch (a 🧪 row in "Na gałęziach"). Inputs: the run note (Roland's note verbatim: review findings and/or the ❌/💬 rows), the task report, the part of the sheet in the task file and any filled-in sheet of the cycle (read only).
1. The branch `spec/<date>-task<NN>` exists and is not merged. Its own branch copy (named in the contract) stands on the branch and is clean; if not, stop and report. One short `--headless --path <worktree> --import` before the tests.
2. Fix only what the findings name, following `CLAUDE.md`. A finding that needs a design decision, or a ❌/💬 row asking for something new, is not a fix: write a decision card (`STATUS: czeka-na-decyzje`). New gameplay goes through the spec first.
3. `test-runner` on the touched scenarios (plus `unit lint dialogue` when lines or ids changed), never the full suite without approval; `convention-reviewer` on a non-trivial diff.
4. Append `## Poprawki (<RRRR-MM-DD>)` to the task report in the main copy: what each finding got (fixed, or why not) and the actual test results. Touch the spec only if a rule, a `[ROBOCZE]` detail or a "Dla agenta" pointer changed (lint, `cli.ts commit` with explicit paths, push).
5. Commit on the branch as `task_NN: poprawki …`. Do not call `ledger` in a fix (the row stays 🧪). Never fill, clear or re-mark a human zone; the ❌/💬 rows stay as written, and the person re-checks. If a fix changes what the person must check, update `## Część arkusza` in the task file (the rows, never human cells). There is no build after the run: the cycle's build comes after the merges.
